Reviewed the complete working implementation: collector, normalization, SQLite

The audit was performed by one agent using the software-engineering review and

Application code, schema, dependencies, and collection policy were not changed.

## Findings

### A1 — P1: a restarted worker can bypass a service Retry-After cooldown

**Location:** [collector.py](../hippos_analyst/collector.py), lines 122–129;
job selection at lines 73–74.

For a 503 response, the worker writes `next_attempt` only on the failed job and
returns. It does not set a service-wide cooldown. Starting another run selects a
different due job and can contact the same service before its requested wait ends.
The 401/403/429 persistent-stop behavior is separate and passed its tests.

**Reproduction:** seed two calendar jobs in a temporary database. A fake fetch
returns HTTP 503 with `Retry-After: 120` on the first request. Close/reopen SQLite
and run the worker again with the same fake clock. Observed:

```text
first outcome: retry
second outcome: limit
first request:  /race/search/2025-10-22/2025-10-22/ at t=0
second request: /race/search/2025-10-21/2025-10-21/ at t=15
requested cooldown: 120 seconds
control.paused_until: 0
```

This conflicts with the project's intent to respect provider-directed waits.
[RFC 9110 section 10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)
describes Retry-After on 503 as the period the service is expected to be unavailable
to the client. The reproduction used no external requests; all live responses in
this archive were 200.

**Remedy:** persist a service-wide not-before time and check it before reserving
any request, including after restart. Keep persistent manual/provider refusal
stops distinct from a timed transient cooldown.

**Acceptance:** with two queued paths and a reopened database, neither path may
be fetched before a 503 Retry-After expires. Cover both seconds and HTTP-date
headers, while preserving the existing manual-pause and 429 behavior.

### A2 — P2: a one-day read loads the entire archive and repeatedly scans requests

**Location:** [server.py](../hippos_analyst/server.py), lines 24–30, 70–73,
87–96; [store.py](../hippos_analyst/store.py), request indexes near line 51.

`calendar()` filters after `self.meetings` has materialized every visible meeting,
every race, and each field's latest snapshot. `meeting()` and therefore `race()`
also use that whole-archive property. Each `head()` query lacks a supporting path
index; SQLite's query plan reports `SCAN r` on the request ledger. The per-Archive
cache is discarded at the next HTTP request.

**Reproduction:** disposable SQLite databases, one meeting per day, ten races per
meeting, ten runners per race, and one successful observation per endpoint.
Request only the final day. All cases return exactly one meeting:

| Stored meetings | Request rows | SELECTs per one-day call | Current read, seconds | Diagnostic path-index read, seconds |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 120 | 132 | 0.0024 | 0.0019 |
| 100 | 1,200 | 1,302 | 0.0425 | 0.0244 |
| 365 | 4,380 | 4,747 | 0.3682 | 0.0817 |
| 1,000 | 12,000 | 13,002 | 2.2168 | 0.2426 |

These are single local diagnostic measurements, not production benchmarks or
latency guarantees. Both timed variants enabled the same SQL trace callback.
The index was added only to the disposable database. The synthetic fields are
smaller than many real fields, and the fixture has no repeated refresh history.
The deterministic query-count growth and query plan establish the problem
independently of exact wall-clock timing.

A captured calendar navigation makes three sequential local requests: overview,
calendar, and race. Each constructs its own Archive. Every horse/search route
also requests the expensive overview before its own data. This is already
documented as a scaling limitation; the audit now supplies measurements.

**Remedy:** filter meetings/races in SQL before expansion; support latest-success
lookups with an appropriate index; compute overview counts without decoding every
runner field. Preserve current membership and observation-time semantics.

**Acceptance:** a one-day/one-race request must not load unrelated historical
fields. Compare equivalent results and query work at several archive sizes,
including repeated observations, removals, and restored deduplicated snapshots.

### A3 — P2: scalar type changes can silently change scratch/result meaning

**Location:** [api.py](../hippos_analyst/api.py), lines 94–104 and 151–170;
consumers in [model.mjs](../hippos_analyst/web/model.mjs), `hasResult`, and
[server.py](../hippos_analyst/server.py), `race_list`.

The allowlist rejects nested values but generally accepts any scalar type.
`absent: "false"` passes normalization unchanged. Both Python and JavaScript
then treat that nonempty string as true, marking the runner absent and suppressing
its results. A boolean program number is also accepted and stored as `"True"`.

**Reproduction:** replace only `absent` in an otherwise valid runner fixture with
the string `"false"`; `normalize()` accepts it. The frontend model returns
`hasResult({placing:'1', absent:false}) === true` but returns false for the same
record with `absent:'false'`.

This is a verified schema-drift handling defect, **not observed live corruption**.
All 1,195 current entries have a JSON boolean `absent`; none has the string form.
The point is to stop on an incompatible upstream change rather than save a
plausible but semantically wrong result.

**Remedy:** validate types for fields that drive behavior, particularly booleans
and participant identity. Reject incompatible values with SchemaError. Decide
explicitly whether missing/null values are valid rather than coercing them.

**Acceptance:** a malformed field refresh must pause, preserve the prior current
field, and archive no successful replacement. Valid string placings, ties, and
source result codes must remain accepted.

### A4 — P2: track filtering steals focus during keyboard selection

**Location:** [app.mjs](../hippos_analyst/web/app.mjs), lines 147 and 232–236.

The track select submits on every change. Rendering replaces the select and
focuses the page heading, because filter submission has no selected-day parameter.
Using ArrowDown therefore changes one option and removes keyboard focus from the
control. A user cannot keep stepping through tracks with successive arrow keys.

**Reproduction in Chrome:** focus Rata on Kaikki radat, press ArrowDown once,
and wait for the local requests to settle. The selected track becomes H and
`document.activeElement` becomes the Kilpailukalenteri H1, rather than SELECT.

**Remedy:** retain the control and focus across filtering, or restore the
equivalent select after rendering; keep automatic filtering if desired.

**Acceptance:** several arrow-key track changes remain possible without tabbing
back to the filter. A deliberate race selection should still move focus to its
racecard on a phone.

### A5 — P2: an empty week removes both week-navigation controls

**Location:** [app.mjs](../hippos_analyst/web/app.mjs), calendar template at
line 71 and its empty-state branch.

The previous/next-week links live inside the nonempty-meeting branch. Clicking
into a week with no collected meetings removes both controls. The user must use
browser Back, manually edit dates, or leave the range to continue browsing.
This breaks the documented one-click week-navigation flow exactly where partial
collection makes empty weeks common.

**Reproduction:** filter to H, view 21–28 October 2026, and click Seuraava viikko
twice. At 4–11 November the empty state is shown and `.week-arrow` count is zero.

**Remedy:** put range navigation outside the conditional results area.

**Acceptance:** previous and next week remain available for populated, filtered
empty, and never-collected ranges, preserving the track filter in each direction.

### A6 — P2: muted text on the page background misses normal-text contrast

**Location:** [styles.css](../hippos_analyst/web/styles.css), root background
and `--muted` at lines 1–8, with `.page-heading p`, `.archive-summary`, and
`.freshness` consumers.

Chrome computed foreground `rgb(102,118,110)` on background `rgb(245,246,242)`
for the introduction, archive summary, and observation timestamp. These render
at 13, 12, and 11 CSS pixels respectively. The computed contrast is **4.4156:1**,
below the 4.5:1 threshold for normal text in
[WCAG 2.2 SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
The threshold is not rounded up. The same foreground on white is 4.7929:1 and
passes; this is a specific background combination, not a claim that all muted
text fails.

**Remedy:** darken the muted text token enough for its lightest-contrast surface,
and check secondary text on selected and hover surfaces too.

**Acceptance:** normal informational text meets at least 4.5:1 in its actual
rendered states. This measured finding does not constitute a full WCAG audit.

### A7 — P3: refreshing discards the chosen result order

**Location:** [app.mjs](../hippos_analyst/web/app.mjs), lines 109, 138,
152–154, and 221.

The sort choice lives only in the replaced select/table. Refreshing reconstructs
them with program order selected. This adds repetitive work when checking results
while data is collected.

**Reproduction:** on Forssa 22 October race 1, select Sijoitus. Nothing Compares
(program 6, place 1) becomes the first row. Click Päivitä näkymä: the select resets
to Lähtönumero and Incanto WF (program 1, place 9) becomes first. The race itself
is unchanged.

**Remedy:** retain the user's sort choice across local refreshes, preferably as
explicit view state. Avoid silently treating a refresh as a new browsing task.

**Acceptance:** refresh updates the data while retaining the selected race and
sort order; decide separately whether expanded horse previews should persist.

### A8 — P3: the horse page's return link discards the originating search

**Location:** [app.mjs](../hippos_analyst/web/app.mjs), search result links at
line 122 and the horse-page return link at line 130.

The visible Takaisin hevosiin link always targets `#/horses`, without the prior
query or page. Browser Back works differently and can restore the search. The
visible return control therefore imposes extra typing/paging on repeated horse
comparisons.

**Reproduction:** search Incanto, open Incanto WF, then use Takaisin hevosiin.
The route becomes `#/horses`, the search field is empty, and the full 1,126-horse
list is shown.

**Remedy:** retain an internal return route for profiles opened from search,
with a sensible fallback for direct links. Keep calendar-origin profiles useful.

**Acceptance:** return from a profile restores the previous query and page;
direct profile links still offer a valid way back to horse browsing.

## Product observations and review limits

The adjacent racecard and inline horse history reduce the main task's navigation
cost. Keep those interactions. On the inspected 390-pixel phone view, the race
detail began about 828 CSS pixels below the page top, after navigation, filters,
and the meeting strip. Collapsible filters or a more compact meeting selector
would make the first field visible sooner. This is a design opportunity, not a
claim that the phone page is broken.

Current result codes, zero-place handling, trial/pony counts, partial history,
and observation timestamps are documented honestly. The codebook and eligibility
semantics still need domain verification before adding interpreted statistics.
Preserve source values and provenance; do not treat opaque result codes as
verified finishing positions or historical backfills as prediction-time evidence.

Veikkaus, weather, favourites, calendar export, and prediction models are planned,
not implemented features. Their absence is not scored as a regression. This audit
did not re-probe third-party endpoints or grant a new interpretation of their
reuse terms. Existing API research remains dated evidence.

No screen reader session, Safari/Firefox run, physical-device test, broad security
penetration test, power-loss experiment, or provider-side completeness comparison
was performed. Keyboard/DOM inspection and contrast calculations are not a full
accessibility certification. Performance fixtures demonstrate the specific query
problem, not a capacity guarantee. The tests were not changed to make them pass.

Recommended correction order: service cooldown, selective/indexed reads and
semantic schema validation, keyboard and empty-calendar navigation, contrast,
then view-state retention. Add focused regression tests for the affected behavior;
do not broaden collection or add prediction complexity to compensate for these
foundation issues.
